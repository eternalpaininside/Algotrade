# Участие в разработке

## Задачи и ветки

Для каждой задачи создавайте отдельную ветку от актуальной `main`:

Укажите цель задачи, ответственного и условия готовности. 

Используйте понятные названия веток:

- `feat/...` — новая функциональность.
- `fix/...` — исправление ошибки.
- `docs/...` — документация.
- `chore/...` — настройка инструментов и обслуживание проекта.

Не отправляйте изменения напрямую в `main`.

## Изменения кода

Старайтесь решать одну задачу в одном pull request. 
Не включайте несвязанные исправления и массовое форматирование посторонних файлов.

Пишите понятные сообщения коммитов, например:

```text
feat(backend): добавил тестирование стратегии
fix(compute): исправил обработку пустого ввода
docs: описание новой функциональности
```

Не добавляйте в репозиторий пароли, токены, содержимое локального `.env`,
зависимости и результаты сборки. Новые настройки документируйте в `.env.example`,
используя безопасные примеры значений.

## База данных

Изменения схемы PostgreSQL оформляйте миграциями. 
Не редактируйте уже применённые общие миграции: создавайте новые. 
Если миграция удаляет или преобразует данные, явно укажите это в PR.

## Проверки

Разработчик компонента отвечает за его тесты и документирует команды их запуска. 
CI автоматически выполняет подключённые проверки.

Перед отправкой на ревью:

- Просмотрите собственный diff.
- Выполните сборку, тесты и остальные доступные проверки затронутого компонента.
- При изменении поведения добавьте или обновите соответствующие тесты.
- При изменении взаимодействия сервисов проверьте затронутый сценарий интеграции.
- Обновите документацию и примеры настроек, если это необходимо.

Если проверку выполнить не удалось, укажите причину в PR.

## Pull request и ревью

Отправьте ветку на GitHub и откройте PR в `main`:

Ответственные за ревью определяются файлом `.github/CODEOWNERS`. 
Автор PR не может одобрить собственный PR:
проверку выполняет другой назначенный владелец кода.

Ревьюер проверяет изменения в пределах своей компетенции. 
При проверке API и интеграции отдельно от внутренней реализации укажите это в ревью.
Корректность реализации и необходимые тесты остаются ответственностью автора.

## Готовность задачи

Задача считается завершённой, когда:

- Необходимые тесты и проверки проходят.
- Контракты, миграции и документация обновлены, если они затронуты.
- PR прошёл ревью и влит в `main`.
